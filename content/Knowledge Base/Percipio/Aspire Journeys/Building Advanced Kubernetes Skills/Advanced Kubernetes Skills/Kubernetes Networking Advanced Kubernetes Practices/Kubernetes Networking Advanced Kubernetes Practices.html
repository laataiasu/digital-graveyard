Kubernetes Networking: Advanced Kubernetes Practices

Several advanced practices can be followed to leverage the full power and rich features of Kubernetes. Among these are those that help take advantage of features, options, and plugins for configuring Kubernetes networking to run efficiently and securely. Take this theoretical and practical course to learn about some of the chief Kubernetes networking components and the features of container network interface (CNI) plugins that implement the Kubernetes networking model. Practice along with demonstrations configuring Flannel and Multus CNI plugins to enable advanced multi-homed pods in Kubernetes. Learn how Kubernetes leverages iptables and routing tables for managing traffic and how load balancing is implemented on Kubernetes clusters. Furthermore, practice configuring network ingress and load balancing in Kubernetes. When you've completed this course, you'll have advanced your Kubernetes networking skills both in theory and in practice.

2. Video: Kubernetes Networking Components (it_akaknpdj_02_enus_02)

Learn how to describe some of the main networking components of Kubernetes networking.

  • describe some of the chief networking components of Kubernetes networking
[Video description begins] Topic title: Kubernetes Networking Components. Your host for this session is Joseph Khoury. [Video description ends]

In this video, we'll explore Kubernetes networking. With Kubernetes, we can leverage the Kubernetes networking model to make the task of communication within a cluster a little bit easier. If you look at it from a container point of view, because we are talking about orchestrating containers, after all, we have a couple of chief considerations.

We consider how to handle container communications internally, and we consider how exactly we're going to expose those containers and really, the applications those containers run, out to the Internet. For container-to-container networking, since containers in the same pod share the same network namespace, it means that they can communicate over the localhost network using different ports.

A network namespace is essentially a virtual networking stack, complete with routes, with firewall rules, and a set of network devices. Incidentally, a host can have multiple namespaces. Now, for pod-to-pod networking, three fundamental principles in Kubernetes networking include, number one, each pod on a Kubernetes node has a unique IP address and can communicate with all other pods in the cluster on any other node, without using network address translation.

Two, any agents running on a specific node, including components like kubelet, kube-proxy, and the container runtime, can access every pod on that node. It just makes sense, because those are the components that manage pods. And third, for platforms like Linux that support pods running in a host network, those pods in the host network can access all pods on all nodes again, without resorting to network address translation.

Now, considering pod-to-service networking. We should understand that Kubernetes pods are ephemeral. They're designed such that they can be replaced as required dynamically. So they come and go as necessary, and as a result, so do their IP addresses. Kubernetes uses services to maintain pod state and track IP addresses, which ensures that requests targeted at a service will be forwarded to the correct pods, and traffic will be distributed amongst pods.

Kube-proxy is a network proxy that runs on each node. It manages and maintains network rules on nodes related to internal and external traffic on the cluster. Kube-proxy uses packet filtering at the operating system level, if one is available, otherwise, it just forwards traffic itself. The way it works, is the service gets its own IP on the cluster.

When a request is made of the service, the request is made to the service IP, and the service then forwards the request onto the correct pods running the requested application that the service is abstracting. This approach is actually a necessity since pods can be created and destroyed all the time, along with the IP addresses that they hold. But, with the service, there is no need to worry about connectivity with any specific pod over time, since the service automatically has its endpoints updated when pods are replaced.

As we know, Kubernetes can be used to provide services out to the Internet. How that is accomplished is dependent on the cluster's infrastructure, and how the cluster networking is implemented. To provide services out to the Internet, it requires a method for external clients to communicate with the service. In cloud-based environments we'll typically have a load balancer that exposes the service to the Internet.

It routes traffic to the service, which then routes and distributes requests to the underlying pods that run the application represented by the service. In Kubernetes, we have network plugins to implement the underlying cluster's networking fabric, and they're called CNI plugins because they align with the specification known as Container Network Interface, or CNI. These types of plugins allow for basic configurations to be generated automatically, and makes administration of the network that much easier.

This is the most common way that Kubernetes networking is configured. Kubenet plugin is a very simple plugin implementing a basic Linux bridge named cbr0. It uses the standard bridge and host-local CNI plugins. This plugin provides functionality that is similar to kubelet's configure-cbr0 command line option. Other networking tools that can work with Kubernetes include Cilium, which is an open-source container network connectivity solution.

It can provide security, networking and observability for container orchestration platforms like Kubernetes, but it's not designed just for Kubernetes. Another popular third-party network implementation for Kubernetes is Flannel. Flannel is a pretty simple implementation that creates a flat network, also called an overlay network, and is deployed as a binary that runs an agent on each host and allocates a subnet lease to each host.

Kube-router is a networking solution that attempts to simplify Kubernetes networking. Using a single DaemonSet or binary, it provides a lean alternative to solutions comprising several networking components. Kube-router is designed for high performance, incorporating Linux Virtual Server, IP Virtual Server technology, for service proxy. Kube-router is designed specifically for Kubernetes.

This means that there is no overhead in kube-router for supporting any other container orchestration platforms, and thus it integrates natively with Kubernetes and CNI plugins. Antrea is another Kubernetes networking solution designed to be Kubernetes native.

Antrea provides networking and security services using Open vSwitch, a high performance virtual switch for pod networking and security. There are also some common cloud vendor CNIs, like AWS VPC CNI, which is the CNI specifically for Amazon Web Services. And there's the Azure CNI for Kubernetes, which is, of course, a CNI designed specifically for Azure.

3. Video: Flannel Container Network Interface (CNI) Features (it_akaknpdj_02_enus_03)

In this video, you will learn how to summarize the features of the Flannel Container Network Interface.

  • summarize the features of the Flannel Container Network Interface (CNI)
[Video description begins] Topic title: Flannel Container Network Interface (CNI) Features. Your host for this session is Joseph Khoury. [Video description ends]

In this video, we'll explore Flannel Container Network Interface. Flannel is a fairly simple networking solution for configuring layer 3 network fabric, and is designed for Kubernetes. Flannel is deployed by running a single binary agent or daemon on each node, called flanneld. We'll have more on that later.

Flannel works by calling the Kubernetes API, or it can also interact directly with etcd, the Kubernetes cluster data store. Here it stores any cluster information like the network configuration, any subnets, the node's public IP, and so on. Flannel pairs with various backends, with the Linux and kernel VXLAN being the recommended pairing.

Usually, VXLAN isn't supported in cloud integrations. However, Flannel does support backend cloud integrations with backends for AWS, Google Cloud Platform, Azure, Ali Cloud and others. Each flanneld agent is responsible for managing a unique subnet for each node. It's also responsible for allotting and distributing IP addresses to each container running on its node, and for mapping container-to-container routes, even across different nodes.

By default, Flannel uses the 10.244.0.0/16 CIDR range across all nodes and allocates a smaller 10.244.X.0/24 CIDR range subnet to each node. That means, by default, each node may have up to 254 active pods, with a unique IP address allocated from the node's subnet networking space. On each Kubernetes pod, Flannel creates two virtual ethernet devices. These are known as veth devices.

A veth device can be used to tunnel between network namespaces, creating a bridge to a physical network device in a different namespace. Flannel uses a Linux network bridge device, cni0, to connect all veth devices, resulting in all pods on the same node being able to communicate with each other. Now, the VXLAN device.

It stands for Virtual Extensible LAN, or VXLAN. This type of device is a virtualized networking device that is designed to provide scalability at levels required by large, cloud-native computing deployments. VXLAN encapsulates layer 2 ethernet frames, within layer 4 UDP datagrams. VXLAN endpoints, also known as VXLAN tunnel endpoints or VTEPs, may be either virtual or physical switch ports and terminate VXLAN tunnels.

What is relevant about VXLANs and Kubernetes networking, is that VXLANs make it possible to connect multiple networks together as if they were connected in the same network. In other words, they provide packet forwarding among nodes in the cluster. OK. Remember the flanneld daemon?

Well, some of the important functions it serves includes managing the unique subnet that has been assigned to a node. It also handles the assignment of IP addresses for each pod on its node, and it is also responsible for ensuring that routes between nodes are accurate and updated as required.

4. Video: Multus Container Network Interface Features (it_akaknpdj_02_enus_04)

During this video, you will discover how to summarize the features of the Multus container network interface plugin for Kubernetes.

  • summarize the features of the Multus container network interface plugin for Kubernetes
[Video description begins] Topic title: Multus Container Network Interface Features. Your host for this session is Joseph Khoury. [Video description ends]

In this video, we'll explore the Multus Container Network Interface plugin. A CNI plugin is a Container Network Interface plugin. As such, any CNI plugin must align with the container network interface specification from the Cloud Native Computing Foundation.

In fact, to be recognized as a CNI plugin, any tool that purports to be CNI-ready, must therefore align with the way that the API between runtimes and network plugins is defined by the specification, providing a network setup for various use cases and implement the Go language library of the CNI specification. Multus CNI is just such a CNI plugin. It works with Kubernetes pods and allows them to have multiple network interfaces attached.

Creating these types of multi-homed pods with multiple interfaces is achieved because Multus CNI acts as a meta plugin, meaning, it can call and use other CNI plugins. As a CNI plugin, Multus CNI must align with the CNI specification. It's deployed as a plugin to help configure the network implementation, and employs the CNI specification as the Go language implementation, which is subsequently used by runtimes.

Now, some of the characteristics of Multus CNI include the fact that it handles the interfacing between CNI plugins and container runtimes. It does not provide the pod network configuration. Rather, it has a dependency on other plugins for that purpose, and indeed uses Flannel, for example, to group plugins into delegates.

Delegates provide a means for providing additional configuration details to plugins, and those additional details could be, for example, specifying a different plugin type altogether, like MACVLAN or IPVLAN, instead of the default delegate bridge plugin. As I mentioned, Multus doesn't provide the pod networking itself.

Rather, Multus supports all reference plugins like Flannel, MACVLAN, and others that implement the CNI specification, and it also supports third-party plugins, like Calico, Weave, and others, for various types of cloud native workloads, and particularly for applications that provide their functionality via network function virtualization. As I mentioned, Multus provides for the creation of multi-homed pods.

We could have, for example, specific types of user traffic on additional network attachments, provided by Multus, but still use the cluster network's master plugin on the pod's eth0 interface, for any communication between Kubernetes services like API Server, kubelet, and others, for tasks like readiness probes and any other interactions between the Kubernetes API and Kubernetes pods.

Multus CNI supports all plugins, supported and maintained within the official GitHub CNI repository and also supports other-third party CNI plugins, like Calico, Cilium, or Contiv. Multus manages plugins as delegates using Flannel, so the plugins can be invoked in a specific sequence. Multus subsequently uses the pod's eth0 interface for the primary or master plugin, with the remainder of the plugins as NETx interfaces.

Because there are various different requirements and use cases for networking pods in Kubernetes, there's an equally varying number of CNI plugins for providing the networking requirements for the cluster. Multus supports the use of multiple plugins. Some of the more popular CNI plugins include Calico, which supports a full networking stack and Kubernetes network policy enforcement.

There's Flannel, which provides a simple overlay network for Kubernetes clusters. Then there's Cilium, which is HTTP aware, and supports Kubernetes network policy. And Weave Net, which runs as a CNI plugin or binary, also supporting Kubernetes network policy. Overall, these CNI plugins allow traffic to pass from the host to different applications on the same host, or on different hosts within the cluster.

Typically, a default pod network using a CNI is configured during cluster deployment. This CNI is referred to as the master CNI and typically appears as the eth0 interface in a Kubernetes pod. This is the interface that provides a path for interaction between Kubernetes services and Kubernetes pods.

What is very convenient about Multus, and actually necessary in some scenarios, is the separation of network interfaces for various reasons and use cases, just like in real physical networks. Say, for example, we have one that's eth0 for Kubernetes pod interaction, but need a second interface for monitoring.

Multus CNI is deployed either by using a DaemonSet, which puts the Multus binary on each node. We can also download the binaries manually from the Multus release page on GitHub, and there's also a Docker image available from Docker Hub. Also, being open source, there's the possibility of acquiring the source, and building and developing from source.

The routing rules determine where packets traversing an IP network will be directed. Any device using Internet protocol uses routing tables.

This includes devices like routers, switches, and I'm including Kubernetes here, although Kubernetes itself is not a device, but it does use routing tables. Information contained in a routing table includes a destination which is the final destination IP address of the packet. The next hop is the IP address where the packet is forwarded onto.

Routing table data also includes the outgoing network interface the device will use, when the packet is forwarded on to the next hop or destination IP. A metric associates a cost with each available route. This way, an optimum path can be selected for the packet that is most cost effective. And, of course, routes. Routes specify any subnets, including those that are directly attached, as well as indirect subnets that are not directly attached, but are accessible over one or more hops.

Routes also include any default routes that will be used for specific kinds of traffic, or if routing information is otherwise incomplete for whatever reason. As discussed, a routing table essentially contains all the information required for forwarding a data packet over the optimum path towards its final destination. And accordingly, each packet has information regarding its source or origin, and its final destination.

Another perspective on routing tables is that they provide a network device with instructions on how to send the packet on to its next hop on the network. Routing table entries can store various types of routes, including directly attached network IDs, remote network IDs, host routes, a default route, and a destination.

Now, considering how routing tables are populated with information, first, any networks directly connected to the device are automatically added. Information for static network devices is static, that is, the entries do not change or change infrequently, and they are added or changed manually by a network administrator.

With dynamic routing, devices build and maintain their routing tables dynamically, leveraging routing protocols to exchange information with other devices regarding the network topology. This basically means that by incorporating dynamic routing tables, devices can actively listen to the network and respond when events like device failures and network congestion occur.

In Kubernetes, the routing table on a node specifies where the packets should be routed to. Let's say the destination happens to be a local pod that resides on the same node. Well, in that case, the packet gets forwarded directly to the local pod's network interface.

If it's not local, then the packet gets forwarded on to the appropriate interface, depending on the type of networking that's being used by the network plugin.
